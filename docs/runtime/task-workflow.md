## 0. Vocabulary

- **Task** — Studio's unit: a first run and its follow-ups (`S/tasks/TaskService.java:50`). **Work** — the core's unit (`WorkId`, one contract, one ledger). **Attempt** — one frozen configuration of a work (`AttemptConfig`, s0, baseline). **Run** — one open of a work until its stop or end (D-430's "run"). **Cell**, **increment** — §4.2, §5.
- **Message** — one user utterance addressed to a work, recorded verbatim with an id (§1.1). Its **kind** ∈ {`request`, `continuation`, `steering`, `amendment`, `answer`} (§2.1). A **decision** is not a message (§2.1).
- **Objective** — the original request plus the amendments, in order (§1.2). **Revision** — `contract.version`; it grows only on an amendment (§2.1).
- **Continue** — the same work and attempt go on. **Follow-up** — a new work in the same task, linked by `parentWork` (§1.3–1.4). **New task** — the host's explicit action; no parent.
- **Goal-level evidence** — evidence of an acceptance item that names the requirement it checks and was not derived by sniffing (§3.1). **Regression obligation** — a green check re-run to show nothing regressed (§4.1 of contracts): the discovered suite, the blast radius, the types of touched files, the full suite, quality gates.
- **Declared output** — a path the task declares as its own output, outside candidate identity from the declaration on (§5.1).

## 1. Intent and task history (№31; WD-24; WF-10, WF-11, WF-13)

### 1.1 What is stored

The **request history** is `contract.requests` — append-only, verbatim, ordered, `UserRequest{id, at, text}` (`K/contract/Contract.kt:33-41`) — extended by W7 with `kind` (§2.1) and `answers` (the id of the question or the `DecisionKey` the message answers, else `null`). Every user message to the work lands there exactly once, whatever its kind, under an id from `IdGen` (`U-n`); a host that retries a delivery passes its own `hostRef`, and a second delivery with the same `hostRef` is recorded once (idempotent). Order is list order; `at` is metadata and never identity or rendering input (I-05). A stored contract whose requests carry no `kind` reads the first as `request` and every later one as `amendment` — that is what every append was until W7 (`K/contract/Contracts.kt:141`).

Three ordered records together are the task history, and the **journal is the ordering authority** across them (`JournalKind.Reconcile` events reference `U-n`, amendment ids and decision keys): (1) the request history above; (2) the **revision history** — one entry per `version`: `{by: user U-n | host(reason) | model AM-n resolved by <authority>}` (`amendByUser`, `amendByHost`, `resolve`: `K/contract/Contracts.kt:141, :155, :170`); (3) **decisions** — records keyed by `DecisionKey` with their request ids (D-428, D-430), referenced from the history by key, never stored as text (WF-8). Model proposals (`AM-n`, D-69) are pending entries of (2). Not stored here: the transcript and the anchor (№34).

### 1.2 The objective

`Contract.objective` is today the latest request's text (`K/contract/Contract.kt:291`, citing D-17; WD-24). W7 defines it as **the original request plus every message of kind `amendment`, in order, each with its id**; the D-17 digest (≤150 tokens, deterministic truncation) excerpts that — the first request's first sentence, then `amended by U-n: <first clause>` per amendment. Steering and continuation messages are pinned verbatim (WF-11) but are not the objective; an answer is evidence unless it amends (D-317, D-344: `changesRequirements`). The requirement graph follows the objective: `R1` is `U1` verbatim (S0 derivation, `K/contract/Contracts.kt:205-234`) and every amendment derives `R-n` verbatim with `authority_ref: U-n` (§2.4). The last text is never the goal. W7 traces every consumer of `objective` (anchor digest, plan packet, review packets, Studio title) and changes none of their contracts beyond the text they receive.

### 1.3 The boundary between continue and follow-up

A work **can be continued** while it is not `Ended` (`CampaignPhase`, `K/campaign/Lifecycle.kt:128-140`) with a **final** outcome. Resumable outcomes: `waiting_for_input`, `waiting_for_process`, `blocked_external`, `budget_exhausted`; final: `completed`, `answered`, `cancelled`. `failed` is final only when the store or the contract cannot be read; an exception inside a cell (the WF-10 limit, `K/campaign/Controller.kt`, `Lifecycle.kt`) ends that cell `Failed` and the run as a resumable stop that names the exception — the next open resumes the increment from its carry (`BoundaryReason.Resume`, `K/context/Manifest.kt:22`; `Controller.kt:1132`). A message to a work that can be continued **continues it** — same `workId`, same attempt — never a new work (№31). A message to a work with a final outcome is a **follow-up**: a new work in the same task with `parentWork` set (§1.4); it never silently continues a finished work, whose candidate was accepted and whose attempt is closed. A **new task** is the host's explicit action and has no parent. A continuation of a resumable stop that no message lifts (a limit still holding) is the C14 rule unchanged: the open reports what holds it and makes no model call.

### 1.4 What the core knows about linked works

Today the link exists only in Studio's database (`parent_work` in `campaign_index`: `S/db/StudioDb.java:37`; `S/campaigns/CampaignService.java:272, :304-305, :344-347`) and `CampaignRequest(work, attempt, text)` carries none (`K/campaign/Controller.kt:279`). W7 adds `parentWork: WorkId?` to `CampaignRequest` and to the stored contract (immutable after the first open), set by the host through `Astrolabe.campaign(project, request, policy, parentWork)` (`K/Astrolabe.kt:111`). The core validates at open: the parent exists in the same project store and has a final outcome; otherwise the open is refused with "work W-n can be continued: resume it" — №31 enforced at the SPI, not by convention. One parent per work; a chain is walked parent-first. Consumers: the finish receipt (`follows: W-n`), `campaign.opened` (`parentWork`), and §4.5 (the parent's register and STATUS into the follow-up's first cell). The pinned requests of a follow-up are its own: Studio's recap (D-430) is the follow-up's `U1` and already carries every ancestor message verbatim — the core adds no second copy.

### 1.5 Invariants and scenario

Secures WF-11 (every run's request holds every user message verbatim, the original first — now also the objective is not the last text), WF-13 (a message to closed-increment work produces work: §2), WF-10 (a resumable `failed`). ## 2. Message kinds (WD-12, WD-13; WF-5, WF-6, WF-8, WF-13)

### 2.1 The five kinds and the decision

| Kind | Meaning | Recorded | Pinned | Revision | Voids | Reaches a model |
|---|---|---|---|---|---|---|
| `request` | the first message of a work | `U1` | yes | 1 | — | yes |
| `continuation` | "go on", "yes", "repeat", an acknowledgement: no new authority | yes | yes | unchanged | nothing | only if work remains: the next cell of an unfinished increment; otherwise the run proceeds to its finish and re-presents the same pending request (WF-5) |
| `steering` | how, not what: order, files to look at, a preference | yes | yes | unchanged | nothing | yes — the running cell's next turn, or the next cell |
| `amendment` | what: requirements, acceptance, constraints, exclusions, scope | yes | yes | +1 | pending completion and decision requests of the old revision are superseded, not deleted (§2.4) | yes — a new increment (§2.4) |
| `answer` | to `task.ask` | yes, `answers = question id` | in the increment's cells | +1 only with `changesRequirements` (D-317) | as amendment when it amends | the asking cell continues |

A **decision** is never a message: it enters through the decision SPI with its `DecisionKey` (D-428, D-430) — `accept`, `accept as is`, `rework(text)`, a limit raise. Free text is never a decision (WF-8). A `rework(text)` of a verified increment or of the campaign is, by the decider's authority, also an amendment: the text is recorded as `U-n{kind: amendment, answers: <key>}` and §2.4 derives the work; today the controller only asks the user to amend (`K/campaign/Controller.kt:1502`).

### 2.2 Who classifies; the default for free text

The **host declares the kind** on the SPI. The user interface makes the kind explicit where it matters: on an open acceptance card the buttons decide and the text field attaches (D-430); on a finished task "continue this task" starts a follow-up and "new task" a new task; an "amend the task" action sends `amendment`. The **model never classifies a user message** (authority); it may only propose what it reads in one (`task.propose(amendment)`, `strengthen`). When the host passes **no kind**, the core derives it from the **work's state, never from the text**:

| State when the message arrives | Default | Effect |
|---|---|---|
| final outcome | the follow-up's `request` | a new work with `parentWork` (§1.3) |
| an acceptance decision is pending (campaign or increment) | note attached to the pending request (D-430) | no decision, no revision change, the same request stands; the card offers decide or amend |
| a cell is running, or a resumable stop with an increment not verified | `steering` (owner question Q1) | pinned; ≥1 model request follows |
| every increment verified, no decision pending, not ended (a limit stop before the final acceptance; the WD-13 open) | `amendment` | revision +1, a new increment, ≥1 model request (WF-13) |

Today every message to a paused work is `amendByUser` (WD-12: version grows, pending completions and decisions voided) and a message to a work whose increments are all closed only unblocks `Blocked` increments (`K/campaign/Controller.kt:683-689`) before the run finds nothing unverified and proceeds to the finish (`:1054`), so no model is asked (WD-13). Under the table a `steering` message during a live run that in fact changes requirements reaches the model but not the ledger; the finish receipt therefore lists every steering message with the cell that received it (`steering: U-4 → cell-9`), and a host that wants the stricter reading sets `CampaignPolicy.defaultMessageKind = Amendment`.

### 2.3 A confirmation is not an amendment

A confirmation is a `continuation` or an attached note. It changes no revision, so the `DecisionKey` is unchanged and a stored accept still applies (WF-6); a pending completion is re-presented under its request id, not voided; a re-entry without new information yields the same stop once (WF-5, D-428). `Contracts.amendByUser` is called for `amendment` only; Studio's "message to a paused work is an amendment" (`S/tasks/TaskService.java`, WD-12) ends with W7's kind on the SPI.

### 2.4 An amendment against closed increments

1. **Verified increments are never reopened.** Their receipts remain regression obligations (contracts §4.1); applicability is computed by the scheduler when later work moves their closure (scheduler §8.1); their `verified` status is harness-derived and changes only through receipts.
2. **The amendment derives work.** `R-n` is the message verbatim (`authority_ref: U-n`); the controller extends the graph with `inc-n` — `depends_on` every verified increment, `accept` = the contract's `run:` items at `scope: touched` plus the goal acceptance the model states (§3.1; the entry gate asks for it) — through the validator `G_single` passes (`K/campaign/PlanNeed.kt:17-27`, contracts §4.2). When the extended single graph fails the validator (S1+ with a `review:` item, a contract touched, an uncovered requirement), the plan cell runs on the amended contract with the verified increments kept as the base of a **replacement graph** (the existing path, `K/campaign/Controller.kt:1575`); cancellations are kept.
3. **Narrowing is never derived from free text.** A removal or narrowing comes only from the host's `amendByHost { apply }` behind an explicit action, or from a resolved model proposal (`AM-n`, pending, never auto-accepted — D-69, `K/tool/task/TaskTool.kt:208-216`); it cancels the requirement with a reason (contracts §4.2), its increment goes `cancelled(reason)`, its receipts stay as history and its regression obligation lapses with the requirement.
4. **Decisions.** `DecisionKey` v3 binds the revision: a request issued for the old revision is **superseded** (its record kept, marked with the new revision) and the campaign end asks anew on the new candidate (D-428 "a strengthened contract re-runs and asks anew"). An accept already applied (a final outcome) is terminal: the amendment is a follow-up by §1.3. Stored results are reused for the same `obligationSet` as today.
5. **Events and journal.** `Contract.Amended(ids, version, by, requestId)`; journal `Reconcile` "amended v<n> by U-n: inc-n added (depends on inc-1…)". Increment-level host answers keep D-317 (unblock without a revision).

### 2.5 Invariants and scenarios

A note attached to a pending decision (row 2 of §2.2) is addressed to the decider, not the executor (D-430: it is never a decision), and reaches a model through the card's "amend" (an `amendment`, ≥1 request) or not at all; a `continuation` to a work with nothing left to do proceeds to its finish without a model call (WF-5). The guard therefore measures rows 3–4 of §2.2 and the follow-up, and no line relaxes it to admit row 2. ## 3. The goal apart from discovered suites (WD-19…WD-23; WF-12)

### 3.1 Goal-level evidence

**Goal-level evidence** is the evidence of an acceptance item that names the requirement it checks and whose creator is not the sniffing harness: a `run:`, `check:` or `review:` item of origin `user` or `amended@vN`; a host item that names a requirement (a host declaring an agent's check as the project's own, plan §4.4 C1b); the model's `model(strengthens R-n)` item — admitted and evaluated (§3.3). **Not** goal-level, whatever their result: the sniffed suite (`origin: harness`, `scope: touched`), the blast radius, the types of touched files, the full suite, quality gates, lint — the regression obligations. `Contract.goalAcceptanceStated` (`K/contract/Contract.kt:297`: any item not of origin `harness`) is the predicate and is today read by nothing (WD-20). W8 reads it in four places: the **entry gate** (`K/cell/Gates.kt:412-426`: today any contract item, the sniffed one included, silences it — D-372 keeps "no plan step needed" for items the contract defines, but a harness-sniffed item is not goal acceptance, so the gate asks for one crisp goal criterion or one question, once); the **sufficiency nudge** (`K/cell/Gates.kt:339-353`: "finish now" fires only when a goal-level `run:` item of the increment is green, never on regression obligations alone); **`PlanNeed.trivialGraph`** (`K/campaign/PlanNeed.kt:17-34`: an S1 contract whose only executable acceptance is sniffed does not skip the plan cell — its reason line says "acceptance is regression only"); the **resolver's class** (§3.2).

### 3.2 A discovered suite is regression evidence

The provenance class (`K/verify/Resolution.kt:289-324`; gates-termination §5.9) today calls a requirement `independent` when a check the host or the user declared passed — and the sniffed suite is `Origin.Harness`, so a green discovered suite alone labels the task "verified independently" (`S/tasks/TaskService.java:980`). W8: `independent` requires at least one **goal-level** declared item (user, amended, or a host item naming the requirement) passed at the final tree and no declared item failed; `agent_test` requires the model's goal-level check passed and nothing declared failed; otherwise `unverified`, and when every regression obligation is green the receipt's `not_verified` line reads "regression only: no goal-level check of R-n" (owner question Q5 on the label). The three wire classes stay (no event or ABI change); each requirement line gains `goal_evidence: [ids]` and `regression: [check ids]`. A requirement whose goal-level item failed is `unverified` with the failure named, and a red regression obligation is a hard refusal as before (§8.5).

### 3.3 The model's goal criterion is admitted and evaluated

The model states a goal criterion as `accept:` on a plan step or through the task tool's acceptance proposal; the controller records it as an acceptance item of origin `model(strengthens R-n)` (`Contracts.strengthen`, `K/contract/Contract.kt:284-288`) — an **addition** and never a weakening, so D-69's `weakening = true` (`K/tool/task/TaskTool.kt:215`) applies to `change`/`remove` proposals only and auto mode does not reject a stated criterion (WD-21). It is **evaluated, not believed**: the scheduler executes it like any `run:` item (receipt, counts, stamps); a `verify` naming it runs it as that item's check instead of refusing an undeclared command (`K/tool/verify/Verify.kt:634-657` today turns such a command into `CHK-model-*` only on `run`); the files it adds are classified by the test-integrity classifier and the `acceptance_surface_model_approved` rules (§5.9, unchanged); its pass yields `agent_test`, never `independent`; a `review:` item, a host declaring it the project's own, or a person's approval lifts it (§5.9). A model item is deleted by nobody (contracts §4.1 "the model may only add").

### 3.4 The path without tests

A repository with no declared suite and no saved command, or a goal with no executable check (a wording change, a configuration, a design note): the entry gate asks for a `check:` item with a named evidence kind (`diff #id`, `refs`, run output) or one question — as today; the ladder (§8.2) applies at L0; the increment ends with the `check:` evidence recorded in STATE and referenced by the Result Packet; the exit gate's §8.7 rule and D-339 apply unchanged: what cannot be verified awaits an acceptance decision, an accept records `accepted`, the class is `agent_test` or `unverified`, the status is `completed`. The absence of a suite is neither a blocker nor a "finish now".

### 3.5 A question task ends with an answer

`answered` (D-344) needs the tree at snapshot 0 and no intent with effects; today `answerable` (`K/campaign/Controller.kt:1254-1264`) reads any non-replay-safe intent as an effect, so a task that ran the tests to answer cannot answer (WD-22). W8 redefines the two conditions, in the controller and the task tool's `answerCheck` (`K/tool/task/TaskTool.kt:90-121`) alike: (1) the **candidate** is at s0 under the attempt's frozen output policy (D-429) — a run that wrote only scratch output moved nothing; (2) **no effect** was recorded: an applied edit, a transform, or a run of W- or D-class (the ladder classes of contracts §4.2) — an R-class run (tests, a build that writes only scratch) is not an effect even though it is not replay-safe (`Intent.replaySafe` keeps its meaning; `effects` is a second predicate from class and stamp). The `answered` receipt lists the runs made as the answer's evidence.

### 3.6 A command saved in Studio

A test command the user saved in Studio is a **user-declared regression check**: `Acceptance.Run(origin: user, scope: all)` with its receipt independent *as regression*. It takes precedence over the sniffed suite of the same package (`B/StudioHost.kt:270-271` `Verification.choose` prefers the sniffed one today, WD-23): the sniffed item is dropped from acceptance when a saved command covers its package and stays `CHK-full` otherwise. It is not goal-level unless the user marks it as checking the goal (owner question Q2). **Node reporters** (C17 item 3): `node --test` with the `spec` and `tap` reporters, and `vitest`/`jest` summaries, are parsed into counts in `K/tool/run/` so a pass is `passed`; the D-50 rule (`K/verify/Scheduler.kt:379-384`: no parsed counts → `inconclusive`) is unchanged — the fix is parsing, never a relaxation.

### 3.7 Integrity flags on `package.json`

`TestIntegrity.surfaceOf` (`K/verify/TestIntegrity.kt:240-248`) classifies the whole manifest as a `CheckDefinition`, so any edit flags every mandatory check (`:165`, `:306`; WD-19). W8: the flag compares the **sections the checks read** between s0 and now — `scripts.<name>` reached by an acceptance command (`scriptPaths`, `:315-316`), the test-runner configuration keys (`jest`, `mocha`, `ava`, `vitest`, `c8`, `nyc`), `workspaces` — parsed, not bytes; a change outside them (`dependencies`, `name`, `version`, `description`) is no acceptance-surface change (a dependency change is caught by the lockfile staying an input, D-429). A person's answer to the model's `task.ask` that names the flagged path and approves the change is recorded as that person's verdict on the flag (`signedBy: user`, reviewer `human`, bound to the path's version like a review, §5.9); free text on a card still decides nothing (WF-8, D-430); a model's answer resolves nothing (`TestIntegrity.kt:34`).

### 3.8 Invariants and scenarios

## 4. What crosses a boundary (WD-27…WD-29, appendix 3; WF-14, WF-15; №33, №34)

### 4.1 The summary of the previous cell comes from the store

At a cell end the controller writes the STATUS note and the checkpoint (`K/campaign/Controller.kt:1592-1602`, `:1640`; `StatusNotes.checkpoint`, `SqliteCheckpoints`), but `carryFrom` takes the previous cell's packet from this run's in-memory list (`Controller.kt:1100`: `packets.lastOrNull { … }`) and a reopened run has none (WD-27). W9: every ended cell's **packet** (register, touched ledger, receipts, dead ends, decisions, open items, `notes_to_persist`, the STATUS revision) is persisted at the cell end in the same transaction as its checkpoint, and `carryFrom` reads packet and register **by cell id from the store**, never from process memory — so a boundary after a reopen produces the same carry bytes as an in-process boundary. The rebuild reasons keep their tails (`K/context/Rebuild.kt`: `Resume` 6, `CellEnd` 0); nothing is summarised by a model (§5.8).

### 4.2 Seeds with a fallback rule

`SeedRule.V1` (`K/Defaults.kt:54`; `K/context/SeedSelector.kt:91-100`) selects entries the next step's text, `accept` or `Next` mention; after a plan mark the next step names no path and the seeds are empty (WD-27). W9: V1 stays the default and keeps its bytes where it yields a candidate (D-398); when it yields **none**, the selector falls back to v2's ranking (touched, red, noted, recent) within the same `seedsMaxTokens`, the carry records `seedReason: fallback` and the cell manifest names the rule applied. Fixtures whose V1 selection is non-empty are byte-identical before and after.

### 4.3 Carry between increments

The first cell of an increment gets nothing today (`Controller.kt:1407`). W9: it receives a **campaign carry** — the previous increment's last validated register without its plan (decisions, dead ends, open items, refuted facts, verbatim), the touched ledger (`path@version`), the last verification status (`CarriedReceipt`), the STATUS note, and seeds by §4.2 from that cell's end export — under the `[K]` carry-forward block, and the resume note names the source ("carried from inc-1 · cell-7"). The within-increment continuation (`Controller.kt:1100-1104`, `:1760-1764`) is unchanged except for §4.1.

### 4.4 Pinned rows append after the transcript

`[T]` renders every pinned row first — the contract's requests, the caller's messages, every question the cell asked (`K/cell/Cell.kt:903-907`) — so a message, an answered question or a review note arriving mid-cell changes every byte after it (WD-28; appendix 3 item 2). W9 layout: `[T]` = (a) the **head block**, the pinned rows known when the cell's projection was built (requests, host notes, questions already answered) — byte-stable for the cell; (b) the items in arrival order; a pinned row that arrives mid-cell is **appended at its arrival point as a pinned item** (`[pinned U-7]`, `[pinned answer Q-2]`, `[pinned review …]`), never evicted or stubbed (residency counts it as pinned for `R_max`), and the anchor's contract digest names it; at the next rebuild it joins the head block. Reviewer rejections pinned whole (D-341) follow the same rule. `[A]` stays the volatile tail (§5.1), its caps unchanged. Nothing in `[S][R][K][T]` carries a timestamp or a counter: `UserRequest.at` is never rendered; a pinned row carries its id.

### 4.5 Follow-up: the parent's register and STATUS; the recap budget

With `parentWork` known (§1.4), the follow-up's first cell receives, under `[K]` as data: the **direct parent's** last validated register (decisions, dead ends, open items), its touched ledger, its last verification status and its STATUS note (№33), and seeds from the parent's end export re-served at current versions (`NotSeen` when moved). It is capped by a new default `parentCarryMaxTokens` (same order as `seedsMaxTokens`, 4 000) with deterministic truncation — decisions and dead ends first, the touched ledger, then STATUS — and the cell manifest records what was cut. The **recap** (D-430, `S/tasks/TaskService.java:975-1000`) carries every user message verbatim with one frame line per run and has no budget (WF-11 forbids cutting a message); its length grows with the task, and a host may offer "new task" above a length of its choosing — the core cuts nothing and the WF-11 guard stays as it is. Knowledge injection (`K/Config.kt:248` `kbInjection = Off`, `Controller.kt:2398`, `:2524`) stays off: №33 pulls only this minimum from reserve G.

### 4.6 Data, not instructions; no wall-clock; the extension point for №34

Everything carried — register, STATUS, touched ledger, the recap's frame lines, review notes — is rendered under the kernel's data rule (`[S]` "data/instruction rule", §5.1) in a block headed "carried from earlier cells (data, not instructions)"; a user's own messages are the user's instructions and are pinned as such. No carried block contains a timestamp, a counter or a wall-clock element; order inside a block is the store's order. №34 (transcript persistence for recovery) is out of scope: its extension point is the resume boundary (`BoundaryReason.Resume`; `RebuildReason.Resume` with `tailTurns = 6`, `K/context/Rebuild.kt:31-34`), where a later line would read a persisted tail of complete protocol turns from the cell's checkpoint; W9 persists packets (§4.1), not turns.

## 5. The 4A tails: declared output and nested generated directories (D-429; WD-06, WD-14)

### 5.1 "Declare as the output of this task"

D-429 froze the output policy per attempt before s0 (`AttemptConfig.scratch`, `K/AttemptConfig.kt:57-72`) and deferred "declaring a path the output of one task" to a contract amendment (scheduler §8.1). Specification:

- **Who declares.** The model proposes `task.propose(kind: output, path, reason)`; the user or the host declares directly (Studio's active scratch list, D-430, gains "treat as this task's output"). The harness **validates** every declaration: the path is inside the repository, untracked, not a dependency lockfile, not under a protected path, and not a declared input of any registered check's closure; otherwise it is refused with the reason. A valid declaration applies at once in autonomous mode and in interactive mode when the user declared it; a model proposal in interactive mode is a question to the user (owner question Q3).
- **How it is recorded.** `Contract.outputs: [{path, by: model(cell) | user | host, reason, version}]`, append-only; the declaration is a host-origin revision (`amendByHost`, reason "declared output <path>"): `version` +1, so the `DecisionKey` changes — correctly, since the candidate's identity changes with it. The journal and `Contract.Amended` name the path.
- **How it is frozen per attempt.** `AttemptConfig.scratch` stays the frozen **base**; the attempt's **effective policy** is the base plus the contract's outputs at the current revision, with id `<base id>+out:<sha256 of the sorted paths, 8 hex>`. The manifest line `scratch-policy=<id>` (`K/workspace/Stamper.kt:123`, `:180`) carries the effective id, so stamps under different declared outputs never compare equal (D-429 encodings hold, no new manifest version); receipts record the effective id as `inputPolicy` and are stale under another (D-429), so the campaign end re-runs what the declaration made stale. A declared path a check names as input stays pinned and re-read (D-374); a tracked path is never excluded (D-429); a declaration is not undone within the attempt. `rewrittenInputs` (D-429) excludes declared outputs from the next check on.

### 5.2 Nested generated directories

`tests/__pycache__` is identity today (D-429: roots anchor at the repository root, nested roots only when declared) and raises integrity flags when a test run writes it. Rule (owner question Q4, recommended): a short built-in set of **generated-directory markers** matches as *any* path segment — `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.hypothesis`, `.tox`, `.nox`, `node_modules`, `.gradle`, `.cache` — and never the generic names (`build`, `dist`, `target`, `out`, `tmp`, `coverage`), which D-429 keeps anchored because `src/build/x` is source. Untracked only: a tracked path under a marker stays in identity (D-374, D-427, D-429), a lockfile under one stays an input, a check's declared input under one stays pinned. This is `ScratchPolicy` version 3 with the marker set inside the policy id; manifests under v3 differ from v2 by the id line only; a running attempt keeps its frozen v2 policy (no receipt goes stale by the upgrade), and a new attempt takes v3. The alternative keeps D-429 as is and relies on §5.1 — every such task declares `tests/__pycache__` by hand.

## 7. Вопросы владельцу

**Q1. Свободный текст во время живого прогона (ячейка работает или возобновляемая остановка с непроверенным инкрементом): что он по умолчанию?**
Варианты: (а) *уточнение* — закрепляется дословно, доходит до модели на следующем ходу, ревизия не растёт, решения и ожидающие завершения не аннулируются; модель, прочитав в тексте изменение требований, предлагает поправку, а интерфейс даёт явное действие «поправить задачу»; (б) *поправка* — ревизия растёт, выводятся `R-n`/`inc-n`, каждое «ок, продолжай» аннулирует ожидающие решения (повторение WD-12), зато требование никогда не теряется из реестра; (в) спрашивать пользователя при каждом сообщении («это уточнение или поправка?»).
Рекомендация: (а) — это урок WD-12 и №35; стоимость ошибки (а): требование, набранное свободным текстом во время прогона, модель выполнит, но приёмка его не проверит, и итог помечен по старому требованию (смягчение: итоговая квитанция перечисляет уточнения с ячейкой, которая их получила); стоимость (б): лишние переоткрытия и повторные вопросы приёмки. Обе стороны обратимы одним флагом `CampaignPolicy.defaultMessageKind`.

**Q2. Считается ли сохранённая в Studio команда тестов свидетельством уровня цели?**
Варианты: (а) нет — это регрессионная проверка, объявленная пользователем (`origin: user`, независимая *как регрессия*); «проверено независимо» по-прежнему требует пункта, который называет требование; (б) да — пользователь объявил её, значит она проверяет цель; (в) по отметке пользователя при сохранении («проверяет цель задачи»).
Рекомендация: (а) — WF-12 говорит о *цели*, а сохранённый набор проверяет проект, не задачу; (в) — дешёвое расширение позже. Стоимость ошибки (а): меньше задач получают метку «проверено независимо»; (б): метка снова не означает проверку цели — тот же дефект WD-20 под другим именем.

**Q3. Кто объявляет «вывод этой задачи» в интерактивном режиме?**
Варианты: (а) предложение модели — вопрос пользователю (`task.ask`-класс с путём и причиной), объявление пользователя или хоста применяется сразу; в автономном режиме проверенное предложение применяется сразу; (б) всегда применяется сразу с видимой строкой в журнале и в Studio; (в) только пользователь, модель не предлагает.
Рекомендация: (а) — объявление меняет идентичность кандидата и ключ решения, это действие уровня поправки; стоимость ошибки (а): лишний вопрос на задачу с нетипичным выводом; (б): модель может вывести из идентичности путь, который пользователь считал результатом (валидатор не отличит `reports/` от `docs/`).

**Q4. Вложенные генерируемые каталоги (`tests/__pycache__`): правило?**
Варианты: (а) встроенный короткий список маркеров-каталогов, совпадающих любым сегментом пути (`__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.hypothesis`, `.tox`, `.nox`, `node_modules`, `.gradle`, `.cache`), только неотслеживаемые; политика версии 3, идущие попытки держат замороженную v2; (б) оставить D-429 как есть — только объявление по §5.1; (в) шаблоны уровня проекта в настройках Studio.
Рекомендация: (а) — закрывает хвост без ручных объявлений, сохраняя «отслеживаемый файл всегда в идентичности»; стоимость ошибки (а): файл в каталоге с таким именем, который проект считает источником, выпадает из идентичности (маркеры выбраны так, что это неправдоподобно; общие имена `build`, `dist` остаются привязанными к корню); (б): каждая python-задача объявляет `__pycache__` сама или получает флаги целостности.

**Q5. Как называть итог, где зелёны только регрессионные наборы?**
Варианты: (а) класс `unverified` с причиной «regression only: no goal-level check of R-n» — три класса на проводе не меняются; (б) новый класс `regression` между `unverified` и `agent_test` (меняет `campaign.finished`, ABI, Studio); (в) оставить `independent` (текущее поведение, WD-20).
Рекомендация: (а) — правдиво и без изменения протокола; стоимость ошибки (а): пользователь видит «не проверено» у задачи с зелёным полным набором и может счесть это сбоем — Studio показывает причину; (б): правка событий и Studio в той же волне.
