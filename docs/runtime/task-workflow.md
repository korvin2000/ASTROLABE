## 0. Vocabulary

- **Task** — Studio's unit: a first run and its follow-ups (`S/tasks/TaskService.java:50`). **Work** — the core's unit (`WorkId`, one contract, one ledger). **Attempt** — one frozen configuration of a work (`AttemptConfig`, s0, baseline, output policy). **Run** — one open of a work until its stop or end (D-430's "run"). **Cell**, **increment** — §4.2, §5.
- **Message** — one user utterance sent to a work, recorded verbatim with an id (§1.1). Its **kind** ∈ {`request`, `continuation`, `steering`, `amendment`, `answer`} (§2.1). A **decision** is not a message; a **note** — text typed with an open acceptance card — is not a message until the card's **Send to agent** (§2.1, D-430).
- **Objective** — the original request plus the amendments, in order (§1.2). **Revision** — `contract.version`; it grows only on an amendment (§2.1).
- **Continue** — the same work and attempt go on. **Follow-up** — a new work in the same task, linked by `parentWork` (§1.3–1.4). **New task** — the host's explicit action; no parent.
- **Evidence purpose** — every acceptance item is `goal` (it checks a named requirement of this task) or `regression` (it shows nothing regressed) (§3.1). **Goal-level evidence** — a current eligible receipt of a `goal` item. **Regression obligation** — a green check re-run to show nothing regressed: the discovered or saved suite, the blast radius, the types of touched files, the full suite, quality gates.
- **Declared output** — a path the task declares as its own output, outside candidate identity from the attempt that freezes it (§5.1).

## 1. Intent and task history (№31; WD-24; WF-10, WF-11, WF-13)

### 1.1 What is stored

The **request history** is `contract.requests` — append-only, verbatim, ordered, `UserRequest{id, at, text}` (`K/contract/Contract.kt:33-41`) — extended by W7 with `kind` (§2.1) and `answers` (the id of the question the message answers, else `null`). Every message sent to the work lands there exactly once, whatever its kind, under an id from `IdGen` (`U-n`); a host that retries a delivery passes its own `hostRef`, and a second delivery with the same `hostRef` is recorded once (idempotent). Order is list order; `at` is metadata and never identity or rendering input (I-05). A stored contract whose requests carry no `kind` reads the first as `request` and every later one as `amendment` — that is what every append was until W7 (`K/contract/Contracts.kt:141`). Notes on an acceptance card live with the card (Studio, D-430) and enter the history only when sent (§2.1).

Three ordered records together are the task history, and the **journal is the ordering authority** across them (`JournalKind.Reconcile` events reference `U-n`, amendment ids and decision keys): (1) the request history above; (2) the **revision history** — one entry per `version`: `{by: user U-n | host(reason) | model AM-n resolved by <authority>}` (`amendByUser`, `amendByHost`, `resolve`: `K/contract/Contracts.kt:141, :155, :170`); (3) **decisions** — records keyed by `DecisionKey` with their request ids (D-428, D-430), referenced from the history by key, never stored as text (WF-8). Model proposals (`AM-n`, D-69) are pending entries of (2). Not stored here: the transcript and the anchor (№34).

### 1.2 The objective

`Contract.objective` is today the latest request's text (`K/contract/Contract.kt:291`, citing D-17; WD-24). W7 defines it as **the original request plus every message of kind `amendment`, in order, each with its id**; the D-17 digest (≤150 tokens, deterministic truncation) excerpts that — the first request's first sentence, then `amended by U-n: <first clause>` per amendment. Steering and continuation messages are pinned verbatim (WF-11) but are not the objective; an answer is evidence unless it amends (D-317, D-344: `changesRequirements`). The requirement graph follows the objective: `R1` is `U1` verbatim (S0 derivation, `K/contract/Contracts.kt:205-234`) and every amendment derives `R-n` verbatim with `authority_ref: U-n` (§2.4). The last text is never the goal. W7 traces every consumer of `objective` (anchor digest, plan packet, review packets, Studio title) and changes none of their contracts beyond the text they receive.

### 1.3 The boundary between continue and follow-up

A work **can be continued** while it is not `Ended` (`CampaignPhase`, `K/campaign/Lifecycle.kt:128-140`) with a **final** outcome. Resumable outcomes: `waiting_for_input`, `waiting_for_process`, `blocked_external`, `budget_exhausted`; final: `completed`, `answered`, `cancelled`. `failed` is final only when the store or the contract cannot be read; an exception inside a cell (the WF-10 limit, `K/campaign/Controller.kt`, `Lifecycle.kt`) ends that cell `Failed` and the run as a resumable stop that names the exception — the next open resumes the increment from its carry (`BoundaryReason.Resume`, `K/context/Manifest.kt:22`; `Controller.kt:1132`). A message to a work that can be continued **continues it** — same `workId`, same attempt — never a new work (№31). A message to a work with a final outcome is a **follow-up**: a new work in the same task with `parentWork` set (§1.4); it never silently continues a finished work, whose candidate was accepted and whose attempt is closed. A **new task** is the host's explicit action and has no parent. A continuation of a resumable stop that no message lifts (a limit still holding) is the C14 rule unchanged: the open reports what holds it and makes no model call.

### 1.4 What the core knows about linked works

Today the link exists only in Studio's database (`parent_work` in `campaign_index`: `S/db/StudioDb.java:37`; `S/campaigns/CampaignService.java:272, :304-305, :344-347`) and `CampaignRequest(work, attempt, text)` carries none (`K/campaign/Controller.kt:279`). W7 adds `parentWork: WorkId?` to `CampaignRequest` and to the stored contract (immutable after the first open), set by the host through `Astrolabe.campaign(project, request, policy, parentWork)` (`K/Astrolabe.kt:111`). The core validates at open: the parent exists in the same project store and has a final outcome; otherwise the open is refused with "work W-n can be continued: resume it" — №31 enforced at the SPI, not by convention. One parent per work; a chain is walked parent-first. Consumers: the finish receipt (`follows: W-n`), `campaign.opened` (`parentWork`), and §4.5 (the parent's register and STATUS into the follow-up's first cell). The pinned requests of a follow-up are its own: Studio's recap (D-430) is the follow-up's `U1` and already carries every ancestor message verbatim — the core adds no second copy.

## 2. Message kinds (WD-12, WD-13; WF-5, WF-6, WF-8, WF-13)

### 2.1 The kinds, the decision and the note — D-433 (Q1)

| Kind | Meaning | Recorded | Pinned | Revision | Voids | Reaches a model |
|---|---|---|---|---|---|---|
| `request` | the first message of a work | `U1` | yes | 1 | — | yes |
| `continuation` | "go on", "yes", "repeat", an acknowledgement: no new authority | yes | yes | unchanged | nothing | yes: the next cell of an unfinished increment; when every increment is closed, a **response increment** (§2.4 A) |
| `steering` | how, not what: order, files to look at, a preference — and every untyped free text short of a final outcome (§2.2) | yes | yes | unchanged | nothing | yes: the running cell's next turn, the next cell of an unfinished increment, or a response increment (§2.4 A) |
| `amendment` | what: requirements, acceptance, constraints, exclusions, scope — **only** the explicit host or user action "change the task", a resolved model proposal, or a `rework(text)` decision; never a default | yes | yes | +1 | pending completion and decision requests of the old revision are superseded, not deleted (§2.4 D) | yes — `inc-n` (§2.4 B) |
| `answer` | to a pending `task.ask` | yes, `answers = question id` | in the increment's cells | +1 only with `changesRequirements = true` (D-317) — then it is also an amendment, appended as an authoritative delta (§4.4) | as an amendment when it amends | the asking increment's next cell continues |

A **decision** is never a message: it enters through the decision SPI with its `DecisionKey` (D-428, D-430) — `accept`, `accept as is`, `rework(text)`, a limit raise. Free text is never a decision (WF-8). A `rework(text)` of a verified increment or of the campaign is, by the decider's authority, also an amendment: the text is recorded as `U-n{kind: amendment, answers: <key>}` and §2.4 B derives the work; today the controller only asks the user to amend (`K/campaign/Controller.kt:1502`).

A **note** — text typed with an open acceptance card — is attached to the card (D-430, WF-8): no message, no revision, no model request, the pending request stands under its key. The card gets an explicit **Send to agent** action: it sends the note as a `steering` message (recorded then as `U-n`, with the card's key in the journal), which opens work and yields a model request (§2.4 A). A note is never promoted silently.

### 2.2 Who classifies; the default for untyped text — D-433 (Q1, Q-card)

The **host declares the kind** on the SPI. The user interface makes the kind explicit where it matters: on an open acceptance card the buttons decide, the text field attaches a note and **Send to agent** sends it; on a finished task "continue this task" starts a follow-up and "new task" a new task; **"change the task"** is the one way to send an `amendment`. The **model never classifies a user message** (authority); it may only propose what it reads in one (`task.propose(amendment)` → pending, `strengthen`). When the host passes **no kind**, the core derives it from the **work's state, never from the text**, and an amendment is never derived:

| State when untyped text arrives | Kind | Transition |
|---|---|---|
| a cell is running | `steering` | pinned at its arrival point (§4.4); the cell's next turn |
| stopped on a pending `task.ask` (`waiting_for_input`, question `Q-n` open) | `answer` to `Q-n`, `changesRequirements = false` unless the host says `true` | the asking increment's next cell (D-317); with `true` also an amendment (§2.4 B), appended as a delta mid-cell (§4.4) |
| stopped with a pending acceptance decision (card open) | **note** on the card — not a message | nothing until the card's decision, or Send to agent → `steering` → response increment (§2.4 A) |
| resumable stop, an increment unfinished (limit, blocked external, a resumable `failed`) | `steering` | the increment's next cell; a limit that still holds is the C14 rule (no model call until raised) |
| resumable stop, every increment verified, no decision pending | `steering` | a response increment (§2.4 A): ≥1 model request |
| final outcome | the follow-up's `request` | a new work with `parentWork` (§1.3) |

A typed kind is honoured when the state admits it: `answer` needs a pending question (else refused), `amendment` is accepted in every state short of final (a pending decision request is superseded, §2.4 D), `continuation` and `steering` follow the table's row for the state. Today every message to a paused work is `amendByUser` (WD-12: version grows, pending completions and decisions voided) and a message to a work whose increments are all closed only unblocks `Blocked` increments (`K/campaign/Controller.kt:683-689`) before the run finds nothing unverified and proceeds to the finish (`:1054`), so no model is asked (WD-13). Because a steering message that in fact changes requirements reaches the model but not the ledger, the finish receipt lists every steering message with the cell or response increment that received it (`steering: U-4 → inc-U4/cell-9`), and the model's `task.propose(amendment)` is the route by which such a message becomes an amendment the user confirms.

### 2.3 A confirmation is not an amendment

A confirmation is a `continuation` or a note. It changes no revision, so the `DecisionKey` is unchanged and a stored accept still applies (WF-6); a pending completion is re-presented under its request id, not voided; a re-entry without new information yields the same stop once (WF-5, D-428). `Contracts.amendByUser` is called for `amendment` only; Studio's "message to a paused work is an amendment" (`S/tasks/TaskService.java`, WD-12) ends with W7's kind on the SPI. No path turns a confirmation into an amendment.

### 2.4 Work from a message to a closed work; amendments, narrowing, decisions

**A. Response increment (continuation, steering, Send to agent).** When every increment is closed, the message gets an increment of its own, `inc-U-n`: `produces: resolves(U-n)` (contracts §4.2 — a user's message is a named uncertainty to resolve, so the node is valid), `depends_on` every verified increment, `accept` = the contract's `regression` `run:` items at `scope: touched` (in the contract, so the entry gate is silent — D-372; the sufficiency nudge stays silent, §3.1). Its cell has the message pinned and the campaign carry (§4.3); it ends by a packet that addresses the message: `done` with no edits (the finish re-presents the pending request under the same key — WF-5, WF-6), edits (the candidate changes, stale receipts rerun at the end, a pending request is voided by the candidate change as any edit voids it), `task.propose(amendment)` (pending for the user — the explicit action), or `task.ask`. No revision, no requirement; verified increments and their receipts untouched. One response increment per message; a second message while one is open is pinned into it (§4.4).

**B. Amendment (explicit).** `R-n` is the message verbatim (`authority_ref: U-n`); the controller extends the graph with `inc-n` — `depends_on` every verified increment, `accept` = the contract's regression `run:` items at `scope: touched` plus the goal acceptance the model states (§3.1; the entry gate asks for it) — through the validator `G_single` passes (`K/campaign/PlanNeed.kt:17-27`, contracts §4.2). When the extended single graph fails the validator (S1+ with a `review:` item, a contract touched, an uncovered requirement), the plan cell runs on the amended contract with the verified increments kept as the base of a **replacement graph** (the existing path, `K/campaign/Controller.kt:1575`); cancellations are kept. **Verified increments are never reopened:** their receipts remain regression obligations (contracts §4.1), applicability is computed by the scheduler when later work moves their closure (scheduler §8.1), and their `verified` status is harness-derived and changes only through receipts.

**C. Narrowing and replacement (user, explicit).** The "change the task" action may carry structured content beside its text: `cancel(R-n, reason)` sets the requirement `cancelled(reason)` and its increment `cancelled(reason)` — texts never change, receipts stay as history, the regression obligation of its items lapses with it; `replace(R-n, text)` sets `R-n.superseded_by: R-m`, appends `R-m` verbatim (`authority_ref: U-k`) and derives `inc-m` as in B. The requirement list is append-only in texts; only status fields move. A steering message never narrows; a model proposal narrows only when the authority resolves it (D-69, `K/tool/task/TaskTool.kt:208-216`, never auto-accepted); a host `amendByHost { apply }` narrows only behind an explicit user action and says so in its reason.

**D. Decisions.** `DecisionKey` v3 binds the revision: a request issued for the old revision is **superseded** (its record kept, marked with the new revision) and the campaign end asks anew on the new candidate (D-428 "a strengthened contract re-runs and asks anew"). An accept already applied (a final outcome) is terminal: the amendment is a follow-up by §1.3. Stored results are reused for the same `obligationSet` as today. A continuation, a steering message and a note change no key.

**E. Events and journal.** `Contract.MessageRecorded(ids, id, kind)`; `Contract.Amended(ids, version, by, requestId)`; journal `Reconcile` "amended v<n> by U-n: inc-n added (depends on inc-1…)" and "response inc-U-n opened for U-n". Increment-level host answers keep D-317 (unblock without a revision).

## 3. The goal apart from discovered suites (WD-19…WD-23; WF-12)

### 3.1 Goal-level evidence: an explicit purpose

Every acceptance item carries a **purpose**, `goal | regression`, and the requirements it checks (`checks: [R-n]`; the existing `Requirement.acceptance` links are the inverse): `goal` — the item checks a named requirement of this task: a `run:`, `check:` or `review:` item of origin `user` or `amended@vN` that names one, the model's `model(strengthens R-n)` item (§3.3), a host item declaring a command the project's own check of `R-n` (plan §4.4 C1b); `regression` — it shows nothing regressed: the sniffed suite (`origin: harness`), a command saved in Studio (`origin: user`, §3.6), quality gates, the full suite, the blast radius and the types of touched files. Origin alone does not decide (today `goalAcceptanceStated` tests origin only, `K/contract/Contract.kt:297`, and §3.6 adds user-origin regression checks): the stored field decides, and a legacy item without one reads `harness → regression`, `user | amended | model → goal` — exactly today's predicate. **`goalAcceptanceStated`** := the contract (for a gate, the increment) has an item with `purpose = goal`. W8 reads it in four places: the **entry gate** (`K/cell/Gates.kt:412-426`: today any contract item, the sniffed one included, silences it — D-372 keeps "no plan step needed" for items the contract defines, but a regression item is not goal acceptance, so the gate asks once for one crisp goal criterion or one question; a response increment, §2.4 A, is exempt); the **sufficiency nudge** (`K/cell/Gates.kt:339-353`: "finish now" fires only when a `goal` `run:` item of the increment is green, never on regression obligations alone); **`PlanNeed.trivialGraph`** (`K/campaign/PlanNeed.kt:17-34`: an S1 contract whose only executable acceptance is `regression` does not skip the plan cell — its reason line says "acceptance is regression only"); the **class** (§3.2).

### 3.2 A discovered suite is regression evidence — D-434 (Q5)

The provenance class (`K/verify/Resolution.kt:289-324`, `K/campaign/FinishReceipt.kt:310-328`; gates-termination §5.9) today calls a requirement `independent` when every declared check passed — and the sniffed suite is declared, so a green discovered suite alone labels the task "verified independently" (`S/tasks/TaskService.java:980`). W8: a requirement is **`independent`** only when every **applicable declared `goal` obligation** that checks it (user, amended, host-declared) has a **current eligible pass at the final tree** — the "every declared passed" rule of `Resolution.requirement` (`:317`) restricted to goal items — and no declared item of either purpose that checks it failed; **`agent_test`** when no declared item failed, no model item failed and at least one of the model's `goal` items (or its own `CHK-model-*` naming the requirement, C1a) passed (today's rule); otherwise **`unverified`**, and when every regression obligation is green the receipt's `not_verified` line reads "regression only: no goal-level check of R-n". A model reviewer's approval of a `review:` item is the agent's evidence (§5.9, owner 2026-10-03) and keeps `agent_test`; only a person's approval, or a host item of purpose `goal`, counts as declared. The three wire classes stay; each requirement line gains `goal_evidence: [ids]` and `regression: [check ids]` as fields with defaults (`RequirementLine`, `FinishReceipt.kt:50`), serialization defaults, ABI regenerated. Red regression obligations keep §8.5 exactly: a red final suite and a **proven new** regression (held failure new against the baseline) are hard refusals; a failure that failed before, an unknown-blast failure and a type failure stay **disclosed `unverified`** (scheduler §8.5; `FinishReceipt.kt:328`) — no sentence here hardens them.

### 3.3 The model's goal criterion is admitted and evaluated — never an authority

The model states a goal criterion as `accept:` on a plan step or through the task tool's acceptance proposal; the controller records it as an acceptance item of origin `model(strengthens R-n)`, purpose `goal` (`Contracts.strengthen`, `K/contract/Contract.kt:284-288`) — an **addition** and never a weakening, so D-69's `weakening = true` (`K/tool/task/TaskTool.kt:215`) applies to `change`/`remove` proposals only and auto mode does not reject a stated criterion (WD-21). It is **evaluated, not believed**, and it **grants no execution authority** (D-262): the command runs only through `run`, under the effect policy, on the model's own authority as today (`K/tool/verify/Verify.kt:481-487` refuses `verify` of a model-added command unless a host or user item approves the same command — unchanged); the scheduler **recognises** the authorized run as the item's check (`recognize`, `Verify.kt:634-657`, C1a) and binds its receipt (counts, stamps, closure) to the item, so the item is evaluated by what ran, never by the model's word. Its test files are classified by the test-integrity classifier and the `acceptance_surface_model_approved` rules (§5.9, unchanged); its pass yields `agent_test`, never `independent` (§3.2). A model item is deleted by nobody (contracts §4.1 "the model may only add"). A host that declares the command the project's own records a host item of purpose `goal` with the same command: from then on the recognised run is declared evidence.

### 3.4 The path without tests

A repository with no declared suite and no saved command, or a goal with no executable check (a wording change, a configuration, a design note): the entry gate asks for a `check:` item with a named evidence kind (`diff #id`, `refs`, run output) or one question — as today; the ladder (§8.2) applies at L0; the increment ends with the `check:` evidence recorded in STATE and referenced by the Result Packet; the exit gate's §8.7 rule and D-339 apply unchanged: what cannot be verified awaits an acceptance decision, an accept records `accepted`, the class is `agent_test` or `unverified`, the status is `completed`. The absence of a suite is neither a blocker nor a "finish now".

### 3.5 A question task ends with an answer

`answered` (D-344) needs the tree at snapshot 0 and no intent with effects; today `answerable` (`K/campaign/Controller.kt:1254-1264`) reads any non-replay-safe intent as an effect, and test runners and builders are **W-class by design** (`K/auth/EffectPolicy.kt:131-138`, `:604-608`: they write caches and artifacts), so a task that ran the tests to answer cannot answer (WD-22). W8 separates **execution authority** from **observed durable effect** and changes only the latter's reading: effect classes, replay classes and `Intent.replaySafe` keep their meaning and their enforcement; a second predicate, `durableEffect`, is derived from the record — an applied edit or transform, a D-class execution, or any execution after which the **candidate** (identity under the attempt's frozen output policy, D-429) differs from s0. `answerable` ⇔ no `durableEffect` ∧ the candidate is at s0 now. A W-class test or build whose observed effect is only scratch output is no durable effect; one that moved the candidate is. The controller and the task tool's `answerCheck` (`K/tool/task/TaskTool.kt:90-121`) use the one predicate; the `answered` receipt lists the runs made as the answer's evidence.

### 3.6 A command saved in Studio — D-434 (Q2)

A test command the user saved in Studio is a **user-declared regression check**: `Acceptance.Run(origin: user, purpose: regression, scope: all)`, independent *as regression*, never goal-level (the user declared the project's tests, not the task's goal). Today `Verification.choose` already prefers the saved test (`B/Verification.kt:56-63`), but Studio bypasses it: the first open calls it only when the core refused a plan with nothing executable (`B/StudioHost.kt:266-270`, a second open — the WF-1 limit), and `expectedVerification` / `verificationOf` report the sniffed suites as "declared" whenever any exist (`:380-390`; WD-23). W8: **one open per action** — the host passes its saved checks into the first open through a `CampaignPolicy.declaredChecks` hook (the core hook the WF-1 limit names), and S0 derivation (`K/contract/Contracts.kt:205-234`) builds the contract with the saved command as the regression item of its package, dropping the sniffed item of that package (the sniffed suite of another package stays; `CHK-full` is unchanged); no `amendByHost` and no second open for a project with a saved command or no checks. `expectedVerification` and `verificationOf` read the stored contract and report by origin and purpose ("saved" for the user's regression item, "declared" for a sniffed one, "review" for none). **Node reporters** (C17 item 3): `node --test` with the `spec` and `tap` reporters, and `vitest`/`jest` summaries, are parsed into counts in `K/tool/run/` so a pass is `passed`; the D-50 rule (`K/verify/Scheduler.kt:379-384`: no parsed counts → `inconclusive`) is unchanged — the fix is parsing, never a relaxation.

### 3.7 Integrity flags on `package.json`

## 4. What crosses a boundary (WD-27…WD-29, appendix 3; WF-14, WF-15; №33, №34)

### 4.1 The summary of the previous cell comes from the store — one atomic cell end

Today the cell runtime persists its terminal checkpoint on every exit path (`settle`, `K/cell/Cell.kt:1402-1408`; `SqliteCheckpoints.save` writes `cells`, `turns` and `workset_exports` in one transaction, `K/cell/Checkpoints.kt:84-95`) and the packet is built afterwards in memory; the controller then writes the STATUS note (`K/campaign/Controller.kt:1592-1602`, `:1640`), but `carryFrom` takes the packet from this run's in-memory list (`Controller.kt:1100`: `packets.lastOrNull { … }`) and a reopened run has none (WD-27). W9 defines the seam: **the cell runtime owns one transaction at `settle`** that writes the terminal checkpoint, the workset export and the **packet row** (`packets`: register at the checkpoint's version, touched ledger, receipts, dead ends, decisions, open items, `notes_to_persist`, `base`, `stamp`) — the packet is built from the checkpoint it persists, never from later state — and the `Cell.Ended` event follows the commit; the **controller** writes STATUS and the journal boundary afterwards (`StatusNotes`, `KbWriter`), idempotent by revision (`carryFrom` already checks `status.archived(...)`). One writer per table (L9): `cells`, `turns`, `workset_exports`, `packets` — the cell runtime; `status` notes and the journal — the controller. **Recovery:** a reopen that finds an ended `cells` row without its `packets` row (a crash inside the old two-step) builds the carry from the checkpoint and export alone and records `packetMissing` in the manifest; a packet without STATUS gets its STATUS written at the next boundary. `carryFrom` reads packet and register **by cell id from the store**, never from process memory, so a boundary after a reopen produces the same carry bytes as an in-process boundary. The rebuild reasons keep their tails (`K/context/Rebuild.kt`: `Resume` 6, `CellEnd` 0); nothing is summarised by a model (§5.8).

### 4.2 Seeds with a fallback rule

`SeedRule.V1` (`K/Defaults.kt:54`; `K/context/SeedSelector.kt:91-100`) selects entries the next step's text, `accept` or `Next` mention; after a plan mark the next step names no path and the seeds are empty (WD-27). W9: V1 stays the default and keeps its bytes where it yields a candidate (D-398); when it yields **none**, the selector falls back to v2's ranking (touched, red, noted, recent) within the same `seedsMaxTokens`, the carry records `seedReason: fallback` and the cell manifest names the rule applied. Fixtures whose V1 selection is non-empty are byte-identical before and after.

### 4.3 Carry between increments

The first cell of an increment gets nothing today (`Controller.kt:1407`). W9: it receives a **campaign carry** — the previous increment's last validated register without its plan (decisions, dead ends, open items, refuted facts, verbatim), the touched ledger (`path@version`), the last verification status (`CarriedReceipt`), the STATUS note, and seeds by §4.2 from that cell's end export — under the `[K]` carry-forward block, and the resume note names the source ("carried from inc-1 · cell-7"). A response increment (§2.4 A) and an amendment's increment get the same. The within-increment continuation (`Controller.kt:1100-1104`, `:1760-1764`) is unchanged except for §4.1.

### 4.4 Pinned rows and authoritative deltas append after the transcript

`[T]` renders every pinned row first — the contract's requests, the caller's messages, every question the cell asked (`K/cell/Cell.kt:903-907`) — so a message, an answered question or a review note arriving mid-cell changes every byte after it (WD-28; appendix 3 item 2); and `[K]` is rendered every turn from the current contract (`ContractSlice.forIncrement(contract, increment)`, `Cell.kt:413`; `K/context/ContractSlice.kt:41-60`), so an answer with `changesRequirements = true` or an amendment mid-cell regenerates `[K]` and breaks the prefix too. W9 layout — a **projection boundary**: `[S][R][K]` and the **head block** of `[T]` (the pinned rows known when the projection was built: requests, host notes, answered questions) are fixed at the projection's build and change only at a rebuild or a cell boundary; (b) the items follow in arrival order; a pinned row that arrives mid-cell is **appended at its arrival point as a pinned item** (`[pinned U-7]`, `[pinned answer Q-2]`, `[pinned review …]`), never evicted or stubbed (residency counts it as pinned for `R_max`); an **authoritative delta** — the contract revision an answer or an amendment produced mid-cell — is appended the same way as `[contract v4 delta] R2 added: …; AC-5 added; AC-1 cwd → …` (the rendered difference of two `ContractSlice`s, byte-stable for equal inputs), `[K]` itself is left as built, and the anchor's contract digest (volatile, §5.1) names the current revision. Harness-side gates, resolvers and the dispatch refusal ("contract changed before verification dispatch", `Verify.kt:481`) read the **current** contract; only the model-facing projection is append-only. At the next rebuild the deltas fold into `[K]` and the pinned items into the head block. Reviewer rejections pinned whole (D-341) follow the same rule. `[A]` stays the volatile tail, its caps unchanged. Nothing in `[S][R][K][T]` carries a timestamp or a counter: `UserRequest.at` is never rendered; a pinned row carries its id.

### 4.5 Follow-up: the parent's register and STATUS; the recap budget

With `parentWork` known (§1.4), the follow-up's first cell receives, under `[K]` as data: the **direct parent's** last validated register (decisions, dead ends, open items), its touched ledger, its last verification status and its STATUS note (№33), and seeds from the parent's end export re-served at current versions (`NotSeen` when moved). It is capped by a new default `parentCarryMaxTokens` (same order as `seedsMaxTokens`, 4 000) with deterministic truncation — decisions and dead ends first, the touched ledger, then STATUS — and the cell manifest records what was cut. The **recap** (D-430, `S/tasks/TaskService.java:975-1000`) carries every user message verbatim with one frame line per run and has no budget (WF-11 forbids cutting a message); its length grows with the task, and a host may offer "new task" above a length of its choosing — the core cuts nothing and the WF-11 guard stays as it is. Knowledge injection (`K/Config.kt:248` `kbInjection = Off`, `Controller.kt:2398`, `:2524`) stays off: №33 pulls only this minimum from reserve G.

### 4.6 Data, not instructions; no wall-clock; the extension point for №34

Everything carried — register, STATUS, touched ledger, the recap's frame lines, review notes, contract deltas — is rendered under the kernel's data rule (`[S]` "data/instruction rule", §5.1) in a block headed "carried from earlier cells (data, not instructions)"; a user's own messages are the user's instructions and are pinned as such. No carried block contains a timestamp, a counter or a wall-clock element; order inside a block is the store's order. №34 (transcript persistence for recovery) is out of scope: its extension point is the resume boundary (`BoundaryReason.Resume`; `RebuildReason.Resume` with `tailTurns = 6`, `K/context/Rebuild.kt:31-34`), where a later line would read a persisted tail of complete protocol turns from the cell's checkpoint; W9 persists packets (§4.1), not turns.

## 5. The 4A tails: declared output and nested generated directories (D-429; WD-06, WD-14)

### 5.1 "Declare as the output of this task" — D-435 (Q3)

D-429 froze the output policy per attempt before s0 (`AttemptConfig.scratch`, `K/AttemptConfig.kt:57-72`; `ScratchPolicy`, `K/verify/Scheduler.kt:72-99`) and deferred "declaring a path the output of one task" to a contract amendment (scheduler §8.1). Specification:

- **Who declares.** A **user or host declaration** applies at once (a visible journal line and a Studio line on the active scratch list, D-430). A **model proposal** `task.propose(kind: output, path, reason)` is, in ask mode, a question to the user (`task.ask`-class, naming path and reason); in autonomous mode it is **refused** unless the policy explicitly allows auto-declaration (`CampaignPolicy.autoDeclareOutputs`, off by default), and the refusal names the policy. The harness **validates** every declaration: the path is inside the repository, untracked, not a dependency lockfile, not under a protected path, not a toolchain directory, and **not a declared input of any registered check's closure**; otherwise it is refused with the reason.
- **How it is recorded.** `Contract.outputs: [{path, by: model(cell) | user | host, reason, version}]`, append-only; the declaration is a host-origin revision (`amendByHost`, reason "declared output <path>"): `version` +1, so the `DecisionKey` changes — correctly, since the candidate's identity will change with it. The journal and `Contract.Amended` name the path.
- **Frozen before s0, applied from the next attempt.** The attempt's **effective policy** = the frozen base (`AttemptConfig.scratch`) plus the contract's outputs **at the attempt's open**, frozen before `s0` like the base (D-429) and used by every stamp, snapshot, drift list and scheduler of the attempt. A declaration made **mid-attempt** is recorded in the contract and takes effect **at the next attempt**; the current attempt's identity, receipts and keys do not move. A user or host may instead **apply now**, explicitly: that ends the attempt and opens the next one on the current tree — a new `s0` under the new effective policy, the baseline per §8.5, the old attempt's receipts kept as history — a visible, journalled step, never implicit.
- **Encoding.** The effective policy's id is `Digest.ofUtf8(CanonicalEncoding.encode("scratch-policy", version, roots…, outputs…))` — the full canonical digest in the scheme `ScratchPolicy.id` uses (`Scheduler.kt:97-99`), with the sorted output paths as `output` entries; no truncation. The manifest line `scratch-policy=<id>` (`K/workspace/Stamper.kt:123`, `:180`) carries it, so stamps under different declared outputs never compare equal (D-429 encodings hold, no new manifest version); receipts record it as `inputPolicy` and are stale under another (D-429).
- **What stays protected.** A tracked path is never excluded (D-429). A path a check's closure names as input cannot be declared (validation above), stays pinned and re-read, and is never exempted from `rewrittenInputs` (D-374): the exemption reaches only paths outside every registered closure. The `DecisionKey` v3 binding of pinned outside inputs is unchanged: an outside input a check reads stays in the key whatever its declaration.

### 5.2 Nested generated directories — D-435 (Q4)

`tests/__pycache__` is identity today (D-429: roots anchor at the repository root, nested roots only when declared) and raises integrity flags when a test run writes it. Decided: a short built-in set of **generated-directory markers** matches as *any* path segment — `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.hypothesis`, `.tox`, `.nox`, `node_modules`, `.gradle`, `.cache` — and never the generic names (`build`, `dist`, `target`, `out`, `tmp`, `coverage`), which stay anchored at the root because `src/build/x` is source. **Untracked only**: a tracked path under a marker stays in identity (D-374, D-427, D-429), a lockfile under one stays an input, a check's declared input under one stays pinned, and a toolchain directory in the tree is not scratch. This is `ScratchPolicy` version 3 with the marker set inside the policy id; manifests under v3 differ from v2 by the id line only; **a running attempt keeps its frozen v2 policy** (no receipt goes stale by the upgrade) and a new attempt takes v3.

## 7. Вопросы владельцу — решены 2026-10-07 (D-433…D-435; план §11 №37–№39)

**Q1. Свободный текст во время живого прогона — что по умолчанию?** Варианты были: (а) уточнение; (б) поправка; (в) спрашивать каждый раз. **Решено: (а) с уточнением владельца.** Нетипизированный свободный текст = `steering`: закрепляется дословно, доходит до модели, ревизия не растёт, решения остаются, итоговая квитанция перечисляет уточнения с ячейкой. Поправка — **только** явное действие хоста/пользователя «изменить задачу»: ревизия растёт, новый инкремент. Подтверждение ничего не меняет. Ни в одном состоянии нетипизированное сообщение не становится поправкой (строка «все инкременты закрыты» §2.2 — тоже `steering`, работа идёт через инкремент-ответ §2.4 A). Флаг `defaultMessageKind` снят.

**Q-card (новый). Текст при открытой карточке приёмки.** **Решено:** текст прикрепляется к карточке (D-430, WF-8); у карточки явное действие «Отправить агенту», которое открывает работу и даёт запрос к модели. WF-13 считает сообщения, *отправленные исполнителю* (каждое явное отправление / уточнение / поправка работе с закрытыми инкрементами даёт ≥ 1 запрос к модели); заметка, ждущая на карточке, — не отправление. Сохранённая в Studio команда тестов — свидетельство уровня цели?** Варианты: (а) нет — регрессия `origin user`; (б) да; (в) по отметке пользователя. **Решено: (а)** как умолчание (ревьюер и исполнитель согласны): регрессионная проверка, объявленная пользователем, не уровня цели; §3.1 даёт ей явную цель `regression`.

**Q3. Кто объявляет «вывод этой задачи» в интерактивном режиме?** Варианты: (а) предложение модели — вопрос пользователю, объявление пользователя/хоста — сразу; (б) всегда сразу с видимой строкой; (в) только пользователь. **Решено: (а) с поправкой Codex:** объявление пользователя/хоста применяется сразу (видимая строка); предложение модели в режиме ask — вопрос пользователю; в auto — отказ, если политика явно не разрешает авто-объявление (`autoDeclareOutputs`, по умолчанию выключено). Эффективная политика замораживается до s0 попытки; объявление посреди попытки действует со следующей попытки или по явному «применить сейчас» (§5.1).
